Chain of Responsibility Pattern

Learn Chain of Responsibility through a support-ticket routing system. The lesson focuses on how to move from one central routing method to a clean chain of focused handlers.

Real LLD Problem First

Start from the real routing problem before introducing the pattern.

Imagine a SaaS support system that receives billing issues, technical bugs, general questions, and critical security incidents.

What the system must do

  • Receive a support ticket.
  • Decide who should handle it.
  • Escalate urgent incidents before normal routing.
  • Stay easy to extend when new teams appear.

Why this becomes tricky

At first, a few if-else checks feel enough. Then requirements grow: VIP rules, region-specific routing, audit rules, priority routing, and fallback behavior.

Core problem: how do we let multiple handlers attempt a request one after another without one central class knowing every routing rule?
2

Beginner / Naive Design

See the beginner-friendly implementation that slowly turns into a maintenance problem.

The natural first attempt is a central router class. It contains all routing rules in one place. This is realistic, but it becomes the only place that keeps growing.

Why it looks acceptable: for two or three ticket types, this is easy to read. The pain shows up when routing rules start changing independently.

4

Core Mental Shift

Understand the thinking shift behind Chain of Responsibility.

Before Chain of Responsibility, the client thinks: “I will decide who should handle this request.” After applying the pattern, the thinking changes to: “I will send the request into a chain. Each handler gets one chance to handle it.”

Before

SupportDesk.route(ticket) checks billing, technical, security, and fallback rules itself.

After

firstHandler.handle(ticket) delegates the decision across a chain of specialized handlers.

Memorable line: Chain of Responsibility converts one method deciding every case into many handlers each deciding one case.

Design Decision Variants

Valid implementation choices and when to use them.

Interface + base class

Best interview version. Interface defines the contract; base class reuses forwarding.

Pure interface

Good when forwarding rules differ across handlers.

Config-driven chain

Useful when handler order changes by environment or product configuration.

Where Should Validation / Business Logic Live?

Where routing logic ends and business logic begins.

Inside handlers

  • Can this handler process the request?
  • Should this request be forwarded?
  • What is this handler’s focused rule?

Outside handlers

  • Database transactions.
  • Complex SLA calculation services.
  • Notification and audit side effects.

Pattern vs Similar Patterns

Avoid confusing COR with Strategy, Decorator, or Command.

ComparisonDifference
Chain of Responsibility vs StrategyStrategy chooses one algorithm upfront. COR lets multiple handlers try sequentially.
Chain of Responsibility vs DecoratorDecorator adds behavior by wrapping. COR conditionally handles or forwards.
Chain of Responsibility vs CommandCommand turns a request into an object. COR routes a request across handlers.
12

When Not To Use Chain of Responsibility

Know when this pattern is unnecessary overhead.

  • Only two simple routing cases exist.
  • A lookup map is clearer.
  • All handlers must run every time; that is more like a pipeline.
  • The chain order is confusing and hard to debug.
13

Common Interview Mistakes

Common LLD interview mistakes around handler chains.

  • Making every handler know the whole chain. Each handler should usually know only the next handler.
  • Forgetting fallback. Decide what happens when nothing handles the request.
  • Putting unrelated business logic inside handlers. Keep routing focused.
  • Confusing COR with Strategy. Strategy picks one; COR tries multiple in order.
14

Production Concerns

Real-world concerns: observability, thread-safety, and configuration.

Observability

Log which handler handled or rejected a request.

Thread-safety

Prefer stateless handlers. Guard mutable shared state.

Idempotency

If handlers trigger side effects, repeated requests should not duplicate work.

Configuration

Production chains are often assembled by dependency injection or config.

15

Testing Strategy

What to test in handlers and full chain wiring.

  • Unit test each handler in isolation.
  • Test forwarding behavior.
  • Test full chain order.
  • Test fallback cases.
  • Test critical incidents bypass normal routing.
16

How To Say It In Interview

A polished explanation students can use in interviews.

Interview-ready answer: I would use Chain of Responsibility when a request can be handled by multiple possible handlers and I do not want one central class to know every rule. Each handler gets a chance to process the request. If it cannot, it forwards to the next handler. This keeps routing logic extensible and avoids one growing if-else method. If the routing is very small, I would keep a simple conditional solution instead.
